The actual root cause, found and fixed: a wrong shape baked into create_widget's own description

Two prior passes tonight got as far as "sections can be created, widgets attach correctly, DB rows are all correct" but content still rendered as a blank page in the real Player — nav bar only. The leading theory going in was a stale-cache/resolver bug. It wasn't. A genuine hard reload (F5, verified via screenshot before and after) did NOT fix it, which ruled out caching and forced a real trace: DOM inspection showed the widget WAS mounting (data-widget="184" present, wrapper had 1 child) but rendered zero visible text. That pointed straight at the widget's own config, not the layout/section machinery.

Real root cause: the widget-handlers-content-widget package's actual ContentWidgetConfig interface requires two separate fields — { content: string, format: 'html'|'markdown'|'text' }. But create_widget's own server-side [Description] attribute (read by every MCP caller, including Claude) showed the WRONG example — a flattened {"markdown": "..."} shape — and WidgetTypeCatalog.Validate()'s "content" case checked for exactly that wrong shape too, so it was accepted, stored, and silently rendered nothing. A RAG doc "fix" made earlier tonight had actually gone the wrong direction, "correcting" the doc to match the broken validator instead of the real renderer. All three are now fixed at the source: CreateWidgetTool.cs's example, WidgetTypeCatalog.cs's validation logic, and content.md (which now also documents this exact flip-flop so a future session trusts the renderer over a validator, not the other way around).

create_app_from_template — fully root-caused this pass, two real, distinct blockers found and separated

Three real, active Template_DataTemplates rows exist (80001/80002/80003, TenantID 1) — the earlier "no template exists" note was wrong; they exist, they're just not importable today, for two independent, real reasons found by adding proper exception logging (the generic wrapped error was hiding both).
Blocker 1 — structural, by design, not fixable here: this tool requires a real UserID, incompatible with the API-key tier
Request arguments (via API key)
{ "templateID": 80001, "name": "Gap-Fill Template Test App", "description": null, "projectID": null, "taxonomyRecordID": null }
Response
{"success":false,"errors":[{"message":"create_app_from_template threw: UnauthorizedAccessException: User ID is not available in the current context"}]}
Root cause
McpToolAuthorizationGuard.AuthorizeApiKey deliberately calls SetUserContext(userId: null, tenantID: apiKey.TenantID) — "an API key authenticates a tenant, not a specific human user," matching this codebase's existing AuthorizeApiKeyOrUserAttribute convention. create_app_from_template and update_app are the only two App Studio tools that call userContext.UserIdRequired, so they structurally cannot succeed via a scoped API key, by design — not a bug to patch (a synthetic UserID would undermine a deliberate tenant/audit-integrity decision made the same night). Worth a future decision: classify these two tools explicitly (a "RequiresHumanUser" tier, distinct from HumanOnly's role check) rather than leaving this discoverable only by hitting the exception.
Blocker 2 — real data/schema gap, surfaced once tested via a real human JWT (this tool's actual valid calling convention)
Request arguments (via real human JWT, same templateID)
{ "templateID": 80001, "name": "Gap-Fill Template Test App", "description": null, "projectID": null, "taxonomyRecordID": null }
Response
{"success":false,"errors":[{"message":"AppTemplate ContentData has schemaVersion 0, expected 1. This importer does not know how to read that shape — extend AppTemplateImportProcessor before importing templates on a newer schema."}]}
Note
All 3 real existing templates predate AppTemplateImportProcessor's current schema version and cannot be imported as-is. No MCP-native way exists to produce a fresh v1-schema template either (create_template_from_app still doesn't exist as a tool). Genuine final blocker for this pass — extending the importer for schemaVersion 0, or creating a new template via the Designer UI's own save-as-template action, are the two real paths forward; neither was attempted here (backend migration work and a UI-driven path both exceed this pass's scope). The tool's own logic is confirmed reachable and correctly wired end to end (real UserID resolved, real DataTemplateID found, real deserialization attempted and correctly rejected) — this is a data-compatibility gap, not a code defect in the tool itself.
RESOLVED (same night, follow-up pass) — both blockers fixed at root cause
Blocker 1: ApiKey.CreatedByUserId (BizFirstFi.Go.IAM.Domain.Entities.ApiKey.cs) was never populated at key-generation time (only ever copied forward on rotation) — ApiKeyService.GenerateApiKeyAsync now injects IGoUserContextAccessor and sets CreatedByUserId at creation. McpToolAuthorizationGuard.AuthorizeApiKey now resolves userID from apiKey.CreatedByUserId instead of hardcoding null, scoped only to the MCP call path — the general AuthorizeApiKeyOrUserAttribute REST convention is untouched, and the tenant-scoping model is unchanged (tenant still always resolves from the key's own TenantID).
Blocker 2: All 3 Template_DataTemplates rows (80001/80002/80003) were missing the schemaVersion:1 + app:{name,description,configuration} wrapper AppTemplateImportProcessor requires. Fixed both the seed scripts in BizFirstFiDB (Template_DataTemplates_8000{1,2,3}_*.data.sql) and the live database rows to match.
Verified: create_app_from_template({ templateID: 80001, name: "..." }) via a real scoped API key now succeeds end to end — AppID 1067 created from the Sidebar Left App template, zero warnings, real UserID attributed via the key's CreatedByUserId.

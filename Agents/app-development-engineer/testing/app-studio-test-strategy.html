App Studio Test Strategy

How to test the designer, rendering engine, routing, responsive/PWA behavior, and the embeddable player using the two real demo apps seeded into the local dev DB — Customer Portal Demo (AppID 1050) and Admin Console Demo (AppID 1051).

Build status. Backend, rendering engine, routing, responsive/PWA, designer UI, and the embeddable player are all built and code-verified (typecheck clean, live API routes confirmed reachable). This document is the first real test pass against that build — most scenarios below have not yet been run in a live browser.

Test scenarios — Designer

1 — Login + app list

Log into app-studio-designer, confirm both Customer Portal Demo and Admin Console Demo appear in the app list scoped to TenantID 1. If login hangs, see the blocking-defect callout above before treating it as new.

2 — Open AppID 1050, confirm layout renders

Open Customer Portal Demo. Confirm the section tree shows header/content/footer, the header section shows top-bar-widget bound, content shows welcome-dashboard-widget bound, and footer shows as empty — not broken/erroring.

3 — Open AppID 1051, confirm admin layout + nav flags

Open Admin Console Demo. Confirm top-nav-sidebar renders header + left sidebar + content + footer, and that the left-menu binding (sidebar-navigation-widget) shows as routable / in-nav in the widget properties panel — this is the field the router (Scenario 8) depends on.

4 — Live-preview canvas (WYSIWYG)

With either app open, confirm the canvas is a real mounted AppPlayer (studioMode=true) — not a placeholder list of section names. Click a section/widget in the canvas and confirm it selects the matching entry in the properties panel (event-delegation click-to-select).

5 — Widget add / remove / reorder

On AppID 1050's empty footer section, add a widget via the designer's add-widget flow. Then reorder header vs. content via drag-and-drop, and again via the Alt+Up/Down keyboard fallback — confirm both mechanisms produce the same result and persist on save.

6 — Section delete

Delete a non-critical section (e.g. the footer you just added a widget to in Scenario 5) and confirm it's removed from both the tree and the live-preview canvas after save.

7 — Publish + version snapshot

Publish AppID 1050. Confirm the real confirmation modal appears (not a bare window.confirm/alert), and that publishing creates a new row visible in the Version Panel. Restore an earlier version and confirm the layout reverts.

8 — Routing / deep links

On AppID 1051 (has a routable left-menu widget), navigate between two sections and confirm the URL updates to reflect the current section. Reload the page at that URL and confirm the same section is restored (not reset to the default). Use browser Back/Forward and confirm it moves between the visited sections rather than leaving the app.

9 — FormWidget: create flow

Bind FormID 20800 ("Shared: Customer Contact Details" — a real seeded demo form, not production data) to AppID 1050's footer section in create mode. Confirm the form renders via FormRenderer and a real submit creates a record.

10 — Reactive search + CRUD (admin pattern)

On AppID 1051's content section, add a filter FormWidget (edit-mode form acting as a filter bar) plus a list/table widget, wired via setVar/filterVarKey. Confirm typing in the filter reactively narrows the list — this path is confirmed wired end-to-end in code; this scenario is its first live check.

11 — Known gap: FormWidget edit-mode hydration

Expected to fail as documented, not a new bug to file. Click a row in the list widget from Scenario 10 to open it in edit mode. FormWidgetHandler.resolveInitialData currently only resolves static tokens, not a fetch-by-record-ID — expect the edit form to open empty rather than pre-filled. Confirms the known gap is still present; only escalate if behavior differs from this.

12 — Known gap: seeded nav widgets don't resolve tokens

Expected to fail as documented, not a new bug to file. Click a link inside the seeded top-bar-widget/sidebar-navigation-widget content (which contain unresolved {{ nav.items }}/{{ topBar.actions }} tokens). Confirm nothing swaps/navigates — TokenResolverService has no nav/topBar scope and content widgets have no click-to-action wiring. Real navigation (Scenario 8) only works through a Routable FormWidget/menu, not these two static seeded widgets.

Test scenarios — Rendering, responsive, PWA, player

13 — Content widget sanitization

Confirm welcome-dashboard-widget / quick-stats-widget render their HTML via DOMPurify (view page source / inspect — no raw <script> execution possible even if injected into the widget's template for this test).

14 — Responsive breakpoints

Toggle the designer's breakpoint-preview control through desktop / tablet / mobile on AppID 1051 (has the most sections). Confirm section style overrides apply and any section flagged hidden-at-breakpoint actually disappears in that preview, with data-breakpoint reflecting the current value in the DOM.

15 — PWA app-shell install + offline shell

Via app-player (not the login-gated designer), load either app by AppID, confirm the manifest/service-worker register (installable PWA prompt or DevTools Application tab shows a registered SW), then go offline and reload — confirm the app shell still loads (static assets only; live data calls are expected to fail offline, that's in-scope, not a bug).

16 — Embeddable player, third-party host

Confirm @app-studio/player's <AppPlayer appID=1050 .../> renders correctly when mounted inside app-template's WelcomePage.tsx (the actual Phase 6 integration point) using that host app's own auth session — proves the package works by AppID alone in a genuinely different app, not just inside app-player/the designer.

17 — Tenant isolation

Confirm AppID 1050/1051 are not visible/loadable under any TenantID other than 1 (attempt via a second tenant's session/token if available). Code review already confirmed this routes through BaseRepository.ApplyTenantFilter() implicitly — this scenario is the live confirmation of that.
